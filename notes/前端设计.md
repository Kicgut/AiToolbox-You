## schema和manifest

• 它们解决的是“如何安全、可复现地知道当前 Codex App Server 协议能做什么”。

  schema 是 Codex App Server 当前安装版本生成的完整 JSON Schema，存放在 .artifacts/tmp/protocol/。它描述协议全部字段、请求、响应、通知和审批类型，例如：

  - turn/start 必须有 threadId、input
  - turn/interrupt 必须有 threadId、turnId
  - thread start/resume/fork 的参数和返回结构
  - 原生审批请求/响应的字段

  它不进入正式仓库，因为体积大、随 CLI 版本变化，而且可能包含与本项目无关的实验性协议定义。

  manifest 是本项目提交到仓库的最小合同，文件是：

  /E:/statistics-toolbox-You/app/ai_workbench/execution/codex_app_server_manifest.json

  它只记录本项目实际依赖的安全子集：

  - schema 版本与 SHA-256 hash
  - experimental_enabled: false
  - 允许调用的协议方法
  - 可处理的原生审批方法
  - turn/start、turn/interrupt 的必要字段

  涉及的项目内容主要是：

  - /E:/statistics-toolbox-You/app/ai_workbench/execution/codex_runtime.py：从 manifest 生成 App Server 方法白名单，防止调用实验性或未确认支持的方法。
  - /E:/statistics-toolbox-You/app/ai_workbench/execution/schema_contract.py：加载并校验 manifest。
  - Runtime Coordinator：依赖该协议执行 New/Resume/Fork、turn 提交、原生 interrupt 和审批桥。
  - Phase 3 测试：验证 manifest 与本机完整 schema hash 一致，并验证运行时只使用 manifest 允许的方法。

  简而言之：完整 schema 是“上游协议事实”；manifest 是“本项目经过审核、允许使用的最小协议边界”。

  • 需要管理更新，但应把“可审计的契约”与“可再生成的原始 schema”分开管理。

  - manifest 必须进入 Git：它是本项目支持的协议基线，记录版本、schema 哈希、允许的方法、必填参数及禁用实验能力。代码会据此限制运行时能力。
  - 完整上游 schema 不进入 Git：当前位于 .artifacts/tmp/...，且 .gitignore 已忽略 .artifacts/*。它是本地生成/校验用的原始证据，不是应用运行的必需依赖。
  - 当前新增的 codex_app_server_manifest.json 和读取它的 schema_contract.py 仍是未跟踪工作文件；后续提交本项目改动时应一并纳入 Git。

  推荐更新流程：

  1. 维护者升级 Codex App Server/CLI 时，生成最新 schema 到 .artifacts。
  2. 用自动校验比对 schema 的哈希、所需方法和参数。
  3. 确认兼容后更新并提交 manifest、兼容代码和测试；原始 schema 继续不提交。
  4. CI 用 manifest 做稳定性校验；发现不兼容则阻止合并，而不是让用户运行时才出错。

  因此，其他开发者或普通用户克隆仓库后：

  - 不需要下载或生成完整 schema，也不需要手工维护 manifest。
  - 正常安装项目依赖即可。
  - 只有要实际启动 Codex 运行时功能时，才需要本机安装并登录受支持的 Codex CLI。
  - 只有负责升级协议的维护者，才需要执行 schema 生成和契约更新流程。

  这样仓库保持轻量、可复现，同时协议变更仍可审查和追踪。

• schema 和 manifest 随“项目代码更新”一起更新，但职责不同：

  - manifest 是仓库内受 Git 管理的最小协议契约。执行 git pull --ff-only origin main 时会自动拿到新版。
  - 完整 schema 不进 Git，位于本机 .artifacts/tmp/protocol/...，用于维护者校验，不会由普通用户下载或更新。

  维护者升级 Codex App Server 兼容性时应：

  1. 用新版已安装的 Codex CLI 生成完整 schema 到 .artifacts/tmp/。
  2. 比对版本、哈希、方法与必填字段。
  3. 更新仓库中的 codex_app_server_manifest.json、适配代码、fixture 和测试。
  4. 通过验证后提交并推送。

  普通用户只需更新仓库；新版 manifest 会自动生效。若其本机 Codex CLI 与新版协议不兼容，应用应报告能力不可用或降级，而不自动升级 Codex CLI。


› 1.所以.artifactis/tmp/的schema会git吗？2.这里的维护者指的是某台设备的维护者，还是仓库的维护者；3.目前本仓库对于多设备部署以及协同是怎么设计的？有什么功能；4.完整schema是否是每个部署该仓库的设备必须的，合适需要更新完整的schema？


• 1. .artifacts/tmp/ 的完整 schema 不会进 Git。

  .gitignore 已忽略 .artifacts/*，所以它只保留在生成它的本机，普通 git pull 不会下载它。进入 Git 的应是最小 manifest，例如：

  - schema 版本与哈希
  - 支持的方法白名单
  - 必填参数
  - 是否允许实验能力

  补充一点：当前工作区中新建的 manifest 文件尚未被提交；它需要随下一次项目提交进入仓库，之后其他设备更新仓库就会自动获得它。

  2. “维护者”指仓库/发布维护者，不是泛指某台设备的使用者。

  同一个人可以在任意一台设备上担任维护者，但他需要负责修改兼容层、更新 manifest、跑测试并推送到官方仓库。普通部署者只拉取已验证的仓库版本，不应自行修改协议契约。

  3. 当前多设备与协同设计是“代码协同、运行隔离”：

   项目代码                       多台设备各自 clone，通过 Git 拉取同一官方仓库版本
  ─────────────────────────────  ─────────────────────────────────────────────────────────────────
   本地设置                       每台设备独立保存，不进 Git
  ─────────────────────────────  ─────────────────────────────────────────────────────────────────
   Workbench 数据库/运行记录      每台设备本地独立，不同步
  ─────────────────────────────  ─────────────────────────────────────────────────────────────────
   Codex/Claude 原生会话          读取各设备自身的本地目录，不跨设备同步
  ─────────────────────────────  ─────────────────────────────────────────────────────────────────
   实时 Run / 审批 / WebSocket    单台机器、单个 FastAPI worker 内有效
  ─────────────────────────────  ─────────────────────────────────────────────────────────────────
   多人协作                       通过正常 Git 分支、PR、提交协作；应用内没有账号、权限或协同编辑
  ─────────────────────────────  ─────────────────────────────────────────────────────────────────
   跨设备复制/迁移会话            规划为 Phase 5，目前未开放

  因此，目前不支持“在设备 A 启动一个 Run、设备 B 接管或查看同一个运行实例”。两台设备可以都运行应用，但状态彼此独立。

  4. 完整 schema 不是每台部署设备的必需文件。

  正常用户只需要：

  - clone / 更新仓库；
  - 安装受支持的 Codex CLI（仅当使用真实 Codex 运行功能）；
  - 使用仓库里的 manifest。

  完整 schema 只在以下情况由仓库维护者生成或更新：

  - 升级本项目支持的 Codex App Server / CLI 基线；
  - 新增、删除或修改 App Server 方法、参数、审批协议；
  - 发现某个 CLI 版本存在协议兼容问题；
  - 发布前重新验证当前支持版本。

  它不需要随着每次 git pull 重新生成，也不需要普通用户手工下载。只有仓库发布了新版 manifest 时，维护者才应重新生成完整 schema、校验哈希和兼容性，然后把 manifest 与代码测试一起提交。

## 更新

• 更新的是“本项目仓库本身”的已提交内容，不是外部工具。

  包括：

  - Python 后端、Vue 前端源码
  - 随仓库提交的前端构建产物
  - 文档、测试、manifest 等项目文件
  - 若 requirements.txt 有变化，重启时同步本项目 Python 依赖

  不会更新：

  - Codex CLI
  - Claude Code
  - CC Switch、Cockpit Tools
  - 本地数据库、会话记录、schema 临时产物或用户配置

  实现方式是 Git 快进更新：

  1. 前端点击“检查更新”。
  2. 后端固定执行 git fetch origin main，再比较本地 HEAD 与 origin/main。
  3. 前端点击“下载并应用”后，后端确认：
      - 官方仓库远端；
      - 当前在 main；
      - 没有未提交改动；
      - 本地没有领先远端；
      - 没有正在运行的 Workbench Run。

  4. 全部满足才执行 git pull --ff-only origin main。
  5. 更新完成后要求重启，run.bat 会按新的 requirements.txt 对齐项目依赖。

  自动更新开关仅让 run.bat 在下次启动前执行同样的安全检查和快进更新；不在应用运行期间偷偷改文件。
