## 前端页面设计前
保留现有 Vue 3 + TypeScript + Vite 技术栈，重做为“左侧应用导航 + 内容工作区”的工作台，而不是引入沉重 UI 框架。你给的三张图适合借鉴其布局语言：柔和浅色背景、清晰留白、圆角信息卡、图标化指标和强弱分明的层级；不会直接照搬其业务视觉。
当前已具备会话中心、统计、受控运行与代理流量入口。主要问题是顶栏导航和内容堆叠，使工作台不像一个可长期操作的产品。
层面	建议

## 前端页面设计后
结论：这套技术栈能完全满足当前视觉方案，不需要更换框架。真正要解决的是前端结构与职责划分，而不是 Vue 或 CSS 能力不足。
保留：
层面	结论
Vue 3 + TypeScript + Vite	合理，适合侧栏工作台、复杂分栏、实时运行流和静态构建发布
Vue Router + Pinia	合理；应新增独立 /runs 路由，并将会话、运行、全局 UI 状态拆分 store
原生 CSS + Design Token	正确选择；当前需要系统化，而不是切换 Tailwind
FastAPI 分发构建产物	合理，生产无需 Node.js，符合既有部署边界
Apache ECharts	适合 Workbench 的统计页；应按需加载 echarts/core，避免全量包
Chart.js	代理流量页已在使用且能力足够，建议保留，不必为统一而重写为 ECharts

需要补齐的不是“大框架”，而是这几项：
CSS 从当前集中式全局样式升级为 tokens / base / components / layouts / utilities 分层；共享颜色、状态、圆角、间距与深浅主题规则。

Workbench 侧采用 lucide-vue-next；代理流量页目前是免构建的 Vue ESM 页面，不建议强塞 lucide-vue-next，可使用同风格的内联 SVG 图标。两边统一视觉规范即可。

当前 [workbench.ts](/E:/AiToolbox-You/frontend/src/stores/workbench.ts) 同时管理会话、搜索、运行、审批、WebSocket 与轮询。视觉改造前建议拆为 session、run、ui 三类 store，避免后续页面越做越难维护。

统计页现有数据接口已经足够支撑 KPI、趋势、质量与拆分展示；先通过统一 API 客户端封装加载、空状态、错误和取消请求即可。@tanstack/vue-query 可作为后续优化，但现阶段不是必需依赖。

质量保障建议新增 Playwright 浏览器验收与 axe 可访问性检查，覆盖侧栏导航、窄屏抽屉、会话筛选、运行审批、统计空状态和代理流量断线/重连。

技术边界应保持清楚：
Workbench SPA：Vue 3 + Vite + Pinia + Vue Router + Lucide + ECharts。
代理流量：保留独立 /traffic 页面、原生 Vue ESM + Chart.js + WebSocket；只共享设计令牌和视觉语言，不合并数据或重写构建链。
不引入 Tailwind、大型组件库或整套后台模板；它们会增加迁移成本，且无法解决当前的状态与信息架构问题。
建议实施顺序是：先做 AppShell + SideNav + Design Tokens，再改会话/运行布局，随后做统计和代理流量页面，最后补浏览器验收。当前工作区存在用户未提交的文档和图片改动；本轮仅做评估，没有修改它们。
