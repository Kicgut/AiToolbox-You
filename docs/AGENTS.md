# docs 文档维护说明

> 状态：生效
> 更新时间：2026-08-01-21-54-08
> 创建时间：2026-08-01-21-25-42
> 适用范围：`docs/` 下所有 Markdown 文档的创建、修订、审查与归档说明
> 不包含：产品代码、数据库数据、原生会话内容、临时运行输出或图像生成过程

`docs/` 保存产品和工程的长期依据，不存放临时运行输出、数据库副本、原生会话内容或截图生成过程。修改代码前，先找到与改动范围相符的文档；设计变更先更新设计文档，再更新受影响的计划与验证规则。

## 文档头部元数据（强制）

每个 `docs/**/*.md` 文档的标题后必须立即使用下列五行，顺序和字段名不得改变：

```md
> 状态：待审查设计提案
> 更新时间：YYYY-MM-DD-HH-mm-ss
> 创建时间：YYYY-MM-DD-HH-mm-ss
> 适用范围：……
> 不包含：……
```

- 时间使用本机 24 小时制，格式固定为 `YYYY-MM-DD-HH-mm-ss`，例如 `2026-07-31-18-05-42`。
- 新建文档时填写五项；修改任何正文后，必须重新核对五项并更新“状态”“更新时间”“适用范围”“不包含”。“创建时间”保持首次创建时刻，除非此前记录错误。
- 既有文档在下一次实质修订时补齐该头部；不得臆造无法确认的创建时间，应从 Git 首次记录或文件元数据核验。
- 状态使用简洁、可判断的值，例如“草稿”“待审查”“已确认”“已完成”“已废弃”“调研结论”。

## 维护规则

- 优先更新已有的权威文档；不要为一次小改动创建重复说明。
- `architecture` 说明“系统应如何工作”，`research` 说明“外部事实如何得出”，`adr` 说明“为什么作出长期决定”。
- `verification-and-boundaries.md` 只说明跨阶段的验证逻辑、顺序和边界；具体测试目录、文件、命令、覆盖缺口和执行结果必须写入 `plans/ai-coding-workbench/` 对应 Phase，并以 `tests/ai_workbench/` 的当前结构为准。
- 新文档使用 Markdown、中文为主，并在开头写清范围；链接使用相对路径。
- 未经用户明确要求，不在 `docs/` 新增 drawio、PNG 或其他图像产物；文本框图优先。
- 改变架构术语时，同步检查仓库根目录 `CONTEXT.md` 和 `plans/ai-coding-workbench/` 中受影响的未实施计划。
- Codex 的仓库级协作规则、项目配置、skill 与本地 memory 的边界归根目录 `AGENTS.md` 管理；不再维护重复的 `codex-project-guide.md`。
