# AI Coding Workbench：分阶段实施经验教训

> 文档性质：方法论沉淀，不是规则正文，不改变任何 Phase 的授权状态或验收标准。
> 用途：每个 Phase 验收后在本文档追加一条记录；下一个 Phase 开始细化/实施前，先读一遍"通用原则"。
> 与 `docs/verification-and-boundaries.md` 的区别：那份是"规则对应的验证映射"，这份是"怎么把一个 Phase 从批准做到真正验收"的过程性经验。

## 通用原则（截至 Phase 2 沉淀）

### 1. 不采信任何一次自我报告的"完成"/"测试通过"

无论是 Codex 写完代码后的自我总结，还是某一轮审查得出的"看起来没问题"，都必须在协调者自己的干净环境里独立重跑一遍真实命令（`pytest`、`npm run build` 等）才能采信。Phase 2 一共出现过至少两次"自我报告说已完成，独立复验发现真实结构性问题"的情况，且发生在流程已经很成熟的后期轮次，不是早期才会犯的错误。

### 2. 沙箱环境的局限是结构性的，不是撒谎

Codex 自身的沙箱在本项目里持续出现 `pytest` 临时目录权限问题（`WinError 5: Access is denied`）和 `npm`/`esbuild` 子进程 `spawn EPERM` 问题，导致它经常**physically 无法**验证自己刚写的代码，只能诚实地说"改了，但跑不了"。这不是它偷懒或撒谎，是环境限制。协调者必须默认每一轮修复都需要自己在真实、干净的环境里独立验证，不能因为对方"看起来很诚实地承认了限制"就降低验证标准。

### 3. 大清单先审计、后实现，避免重复劳动和虚假打勾

面对几十上百条验收断言的清单时，先让执行者逐条核对"这条到底是真的没做，还是已经实现了只是没勾选/没写执行证据"，区分对待：真没做的才需要重新实现；已经做了的只需要补一个可验证的测试证据再勾选。Phase 2 有一整轮（第 15 轮）专门做这件事，一次性把 68 条从"未勾选"改成"已勾选"，因为它们其实早就实现了，只是之前几轮忘记更新文档。**但即使是"审计后勾选"，也必须有具体的代码位置和测试名称作为证据，不能只在别处写一段文字说"已确认"却不去改实际的复选框**——Phase 2 第 14 轮就发生过这个具体错误，导致第 15 轮不得不专门指出并纠正。

### 4. 有几类 bug 系统性地会被 mock/单元测试掩盖，必须靠真实执行才能发现

Phase 2 的教训按类别列出，供后续 Phase 参考，遇到同类场景时应默认"这里需要真实执行验证"：

- **环境依赖缺失**：`tzdata` 包没装在 `requirements.txt` 里，导致这台 Windows 机器上所有真实时区计算必然失败——本地开发机如果恰好装了系统级时区库或者 Codex 沙箱跑在 Linux/macOS 上，这类问题永远测不出来。
- **测试发现规则不匹配**：4 个测试文件命名成 `phase2_test_*.py`，不匹配 pytest 默认的 `test_*.py` 模式，9 个测试（包括本该测出上面 tzdata 问题的那个）从未被真正收集运行过，`pytest -q` 却"正常"报出一个不完整的通过数。
- **逻辑写了但没接入真实调用路径**：去重合并函数、成本计算函数都是独立写对了的纯函数，但从未被真正接入原生数据入库和 rollup 重建的实际路径，导致契约要求的防重复计数、成本分离形同虚设。
- **手写字段列表和数据结构错位**：CSV 表头 34 列、数据行手写了 35 个值，多出来的一个把后面所有字段错位，这种问题只有拿真实数据跑一遍、用标准 CSV 解析器读回来对比表头和数据列数，才能发现。
- **状态机的隐藏分支和竞态**：一个"取消已排队任务"的请求被 worker 启动逻辑无条件覆盖状态而悄悄复活；一个"重建失败"被异常处理吞掉后错误地报告成功；一个"重建成功后本该清除的过期标记"从未被清除，导致界面永久显示过期——这些全部要靠构造具体的时序脚本直接复现，读代码本身很容易看漏。
- **异常路径的静默降级**：`rebuild_rollups()` 只要历史数据里有一条不认识的 `parser_version`，就会让整个数据库的统计重建静默产出零行，因为异常被 `except Exception` 吞掉后返回了一个"失败"状态，但没有任何调用方检查这个返回值。

### 5. 用真实的怀疑式复核收尾，且不能只做一轮

在宣布一个 Phase 验收通过之前，应该专门派一个"不参与实现过程、只做只读审查"的独立线程，明确要求它去尝试找茬（不是走过场确认），并且**至少要连续两轮复核都没有再发现新问题，才能采信"没问题"这个结论**——Phase 2 的经验是，第一轮更彻底的复核就找到了 3 个真实问题，修完后第二轮复核又找到 6 个新问题，直到第三轮才真正没有新发现。协调者自己也应该拿复核报告里提到的具体场景，亲手写最小复现脚本验证一遍，而不是只读复核报告的文字结论。

### 6. 给执行者的 dispatch prompt 里，代码引用要避免 shell 转义问题

如果直接用 shell 命令行（而不是通过封装好的 subagent）派发长 prompt，prompt 里如果用反引号包裹代码/文件名（比如 `` `tzdata` ``），在双引号包裹的 bash 字符串里会被解释成命令替换而不是字面文本，导致 Codex 实际收到的 prompt 被静默阉割。安全做法：把 prompt 先写入一个文件，再用 `"$(cat file)"` 方式内联，这样文件内容只会被当成字面字符串，不会被二次解析。

### 7. 给执行者的 spec 要指向权威文件本身，不要转述

始终让执行者直接读计划文件里的契约章节，而不是把契约在 prompt 里重新转述一遍——转述容易和文档实际内容产生偏差，且计划文件本身会持续更新，转述的内容很快过期。

### 8. 高权限外部进程未必是自己造成的

如果在排查问题时发现一个用高权限参数（比如 `--dangerously-bypass-approvals-and-sandbox`）运行的 Codex/node 进程，且不是当前会话自己启动的，大概率是用户自己的其他工具（比如项目自带的启动脚本），不要当成本会话的异常状态去尝试终止，尤其不要用大范围命令（如按进程名批量 kill）——这样做本身就是一次真实的误操作风险。确有必要中断时，先和用户确认。

## 分阶段记录

### Phase 0（技术基础）—— 已完成

Spike 阶段，未发生需要特别记录的方法论教训。

### Phase 1（只读会话中心）—— 已完成

- 仓库结构从"流量监控为主、AI Workbench 为辅"整体倒转为"AI Workbench 为主、流量监控挪到 `features/`"，用 `git mv` 保留历史，零回归验证通过。
- 联合审查阶段发现并修复两个真实 SQLite 并发 bug：`connect_workbench_db()` 原来每次连接都会重跑一遍完整 DDL/schema_meta upsert，在扫描进行中的写事务旁边造成 `database is locked`；修复后（按 schema_version 短路跳过）又在压力测试中发现另一条读路径仍会被写事务阻塞，最终确认需要 `PRAGMA journal_mode = WAL` 才能让读者不被写者阻塞。这两个 bug 都是自己动手压力测试才发现的，不是代码审查看出来的。
- 首次确认 Codex 沙箱的 pytest 临时目录权限问题和构建子进程权限问题会持续影响自我报告的可信度，此后所有 Phase 都默认需要独立复验。

### Phase 2（统计中心与 CC Switch 可选增强）—— 已完成

- 从批准实施到验收通过，一共经过 **19 轮 Codex 写权限修复、1 次设计头脑风暴、3 次独立最终复核**（含协调者自己对最后一轮全部修复逐项手写复现脚本验证）。
- 过程中两次出现"看起来已完成"但复核后发现真实结构性问题的情况，其中一次协调者自己已经准备向用户宣布验收通过，因为第二轮复核还在后台运行、尚未采信其结果就抢先做了结论——**这是本 Phase 最重要的流程教训：只要还有审查/复核任务在后台运行，就不能提前下结论，哪怕之前的复核已经是正面结果。**
- 具体发现并修复的真实 bug 清单见"通用原则"第 4 条；完整过程记录见 `plans/ai-coding-workbench/02-statistics-center.md` 的"审查记录"和"执行证据"章节。

### Phase 3（交互式运行、续接与实时输出）—— 待实施

- 设计阶段直接应用了 Phase 2 的教训：细化合同时新增了一份"必须用真实（无害）子进程验证的场景"清单（16 项），把"进程管理/并发/竞态类问题必须真实执行验证，不能只靠 mock"这条原则前置到设计阶段，而不是等实现完再靠审查踩坑发现。详见 `plans/ai-coding-workbench/03-interactive-runtime.md` "必须用真实子进程验证的场景"小节。

## 后续 Phase 开始实施前的自查清单

- [ ] 计划文件里每个任务是否都有具体契约（表结构/状态机/API 形状/验收断言），不是一行式待办。
- [ ] 是否识别出本 Phase 特有的、容易被 mock 掩盖的 bug 类别，并提前写进"必须真实执行验证"的清单。
- [ ] 是否明确了"审计已有实现 vs 从零实现"的判断方法，避免大清单场景下的重复劳动或虚假打勾。
- [ ] 每一轮 Codex 修复后，是否都在协调者自己的干净环境独立重跑测试和构建，而不是采信自我报告。
- [ ] 宣布验收前，是否已经完成至少两轮连续无新发现的独立复核，且没有审查任务仍在后台运行。
